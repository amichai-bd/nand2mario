07 · Reproducible builds · 01

PASS is useful only with its inputs

A build result belongs to exact source, configuration, tools and options. The builder retains that identity beside commands, logs and artifacts.

Changing any relevant input changes the evidence identity, even if filenames match.

Explore the reasoning

A reproducible process lets another run explain whether it is testing the same thing. A filename such as latest.log is not enough to establish that relationship.

Source: Build system contract

07 · Reproducible builds · 02

A cache hit is a checked claim

A matching successful result may be CACHED only while its fingerprint and required artifact hashes remain valid.

Fingerprint

Source, target, seed, runner and tool identity.

Evidence

Retained outputs must exist and match their hashes.

Meaning

Reuse performs no fresh simulation or license checkout.

Explore the reasoning

If the RTL stays the same but an Intel model changes, the experiment has changed. Model identity must participate before old evidence can be reused.

Source: Questa simulation and cache rules

07 · Reproducible builds · 03

Change one input, lose the old identity

Consider a changed model file: the old source hash no longer matches. The builder must reject the mismatch or build a newly approved configuration.

Explore the reasoning

A tool path alone is not an identity. Installing a different binary at the same path must not silently preserve a previous PASS.

Source: Intel model resolution

07 · Reproducible builds · 04

A clean software build checks determinism

Springtrail’s foundation records two clean builds with identical bytes and hashes for its 32 KiB mapperless image.

Explore the reasoning

Matching bytes establish reproducible packaging for these inputs. They do not prove the game logic is correct; execution and gameplay acceptance are separate.

Source: GAP-011 foundation evidence

07 · Reproducible builds · 05

Failures are artifacts too

A failed attempt needs its actual command, diagnostic and relevant trace. Suppressing a warning or overwriting the failed run makes diagnosis harder.

Immutable attempt

Keep the run’s identity and original logs.

Useful failure

Record the first expected/actual divergence.

Honest status

A failed smoke stays FAIL; do not relabel it as success.

Explore the reasoning

Some specifically defined expected-failure targets can be validated as such. That rule does not convert an arbitrary failed run into a passing result.

Source: Diagnostics and reuse

07 · Reproducible builds · 06

Build and publication are separate events

The wiki checker creates a local site. Merging main triggers Pages; a completed deploy and the served page establish publication.

Explore the reasoning

Stage new documents before checking: publication reads tracked files. A local build is not a deployment. Inspect the actual workflow result and served deck instead of assuming that a merge made it live.

Source: Wiki build and browser checks
